# PE Lab — Training Manual

> **⚠️ IMPORTANT — READ FIRST**
>
> The IP addresses, hostnames, ports, tokens and passwords shown throughout this
> manual are **examples from one specific build** (Docker host `10.0.0.10`,
> nodes `core0`, `haproxy`, etc.). **They are almost certainly NOT what
> you will see** on your own environment.
>
> Every PE Lab build is different — your Docker host IP, node names, ports,
> tokens and console password will be unique to you.  **Always use the values
> from YOUR OWN `helper.md`** (generated by the wizard at the end of your build)
> instead of the examples here.
>
> Wherever you see a value below, substitute the matching value from your
> `helper.md`.  The *steps* are the same for everyone — only the values differ.

---

## How to use this manual

This manual walks you through the PE Lab environment **step by step**, in the
order you will actually use it.  Each section:

1. Explains **what** the component is.
2. Gives **step-by-step** instructions to reach/use it.
3. Tells you **how to verify** it worked.
4. Lists common **troubleshooting** tips.

Work through the sections in order.  Sections 1–5 get you connected; sections
6–7.9 cover the "nano" add-on services; section 8 covers day-2 operations.

---

## 0. Prerequisites

Before you start, make sure you have:

- The **`helper.md`** file from your build (for your real IPs/hostnames/tokens).
- The **SSH private key** from your build (e.g. `/root/pelab/id_ed25519`).
- A machine that can reach the Docker host on the same internal network.
- The ability to edit `/etc/hosts` on the machine you browse from (root/sudo).

> **Tip:** keep `helper.md` open in a second window and substitute its values
> as you follow along.

---

## 1. Reach the Docker host

The Docker host is the single VM that runs all the PE containers.

**Step 1.** Note your Docker host's internal IP and FQDN from `helper.md`
(example: `10.0.0.10`, `dockerhost.example.com`).

**Step 2.** Confirm you can reach it (ping):

```bash
ping -c 3 10.0.0.10
```

**Step 3.** Confirm you can SSH to it as root with the build key:

```bash
ssh -i /root/pelab/id_ed25519 root@10.0.0.10
```

**Verify:** you get a shell prompt on the Docker host.

> **Troubleshooting**
> - `Connection refused` → the host isn't up yet, or sshd isn't running.
> - `Permission denied` → wrong key, or the key isn't in `authorized_keys`.

---

## 2. Open the PE Console

The PE Console is the web UI for managing Puppet Enterprise.

**Step 1.** On the machine you browse from, add the console hostname to
`/etc/hosts` (use YOUR Docker host IP and primary node name):

```bash
echo "10.0.0.10   core0" | sudo tee -a /etc/hosts
```

**Step 2.** Open the console URL from `helper.md` (example):

```
https://core0
```

**Step 3.** Accept the self-signed certificate warning.

**Step 4.** Log in with the console username/password from `helper.md`
(example: `admin` / the password you set).

**Verify:** you land on the PE Console dashboard.

> **Troubleshooting**
> - Page won't load → check the `/etc/hosts` entry and that the Docker host is up.
> - `ERR_CERT_*` → expected; accept the self-signed cert.

---

## 3. Connect agents

Agents are the machines Puppet manages.  In a LARGE/XL build they connect via
the HAProxy load balancer on port 8140.

**Step 1.** Add the load-balancer hostname to `/etc/hosts` on the agent node:

```bash
echo "10.0.0.10   haproxy" | sudo tee -a /etc/hosts
```

**Step 2.** Install the agent (use YOUR values):

```bash
curl -k https://haproxy:8140/packages/current/install.bash | bash
```

**Step 3.** Run the agent:

```bash
puppet agent -t
```

**Verify:** the agent appears in the PE Console under **Nodes** and reports in.

> **Troubleshooting**
> - Install script fails → check the `/etc/hosts` entry and that 8140 is reachable.
> - Agent can't reach the server → confirm the nodepool/HAProxy hostname resolves.

### Reinstalling an agent (installagent.sh)

Every node carries `/root/installagent.sh`.  It removes any existing agent,
reinstalls one with a role fact, and applies a catalog:

```bash
/root/installagent.sh <puppet_role> <install_url>
/root/installagent.sh pe_compiler haproxy
```

## 4. SSH to each container

Each container's SSH (port 22) is mapped to a unique port on the Docker host.

**Step 1.** Find the container's SSH port in `helper.md` (example table):

| Container | SSH port |
|---|---|
| `core0` | 2201 |
| `core1` | 2202 |
| `core2` | 2203 |
| `core3` | 2204 |
| `compiler0` | 2205 |
| `compiler1` | 2206 |
| `haproxy` | 2207 |

**Step 2.** SSH to a container using its mapped port (use YOUR values):

```bash
ssh -i /root/pelab/id_ed25519 -p 2201 root@10.0.0.10
```

**Verify:** you get a shell on the container (e.g. `core0`).

> **From your laptop:** copy the key over first and `chmod 600` it.

### SSH-key requirements

Before the wizard can connect, every target node must allow the chosen public
key:

1. The public key (`/root/pelab/id_ed25519.pub`) is in the ssh_user's
   `~/.ssh/authorized_keys` (for root: `/root/.ssh/authorized_keys`).
2. `/etc/ssh/sshd_config` has these **uncommented**:
   - `PubkeyAuthentication yes`
   - `AuthorizedKeysFile .ssh/authorized_keys`
3. Permissions allow sshd to read the key (`chmod 700 ~/.ssh`,
   `chmod 600 ~/.ssh/authorized_keys`).

## 6. Local git (gitnano) on the master

Gitnano is a lightweight control-repo manager.  It hosts a bare git repo and a
small HTTP API; r10k/code-manager pulls from it over SSH.

### Where things live

- Bare repo: `/opt/gitnano/repos/control-repo.git`
- Live worktree (the `production` branch): `/var/www/production`
- API: `http://core0:5000`  (Bearer token from `helper.md`)
- r10k SSH key: `/etc/puppetlabs/puppetserver/ssh/id-control_repo.rsa`
- r10k remote: `gitnano@core0:/opt/gitnano/repos/control-repo.git`

### Step-by-step: make a change and deploy it

**Step 1.** SSH into the master (section 4).

**Step 2.** Work in the live worktree:

```bash
cd /var/www/production
git status
git log --oneline -5
```

**Step 3.** Edit a file (e.g. add a class to the default node):

```bash
vi manifests/site.pp
```

**Step 4.** Commit and push to gitnano:

```bash
git add .
git commit -m "test commit"
git push gitnano production
```

**Step 5.** Deploy to PE (r10k pulls the new commit):

```bash
sudo /opt/puppetlabs/bin/puppet-code deploy production --wait
```

**Step 6.** Run the agent to apply it:

```bash
sudo /opt/puppetlabs/bin/puppet agent -t
```

**Verify:** your change is applied on the target nodes.

### Troubleshooting

- `puppet code deploy` fails with `invalid or unknown remote ssh hostkey`:
  set `r10k_known_hosts` (from `helper.md`) on
  `puppet_enterprise::profile::master` and run `puppet agent -t` on the master.
  Regenerate the entry with:

  ```bash
  ssh-keyscan -t ed25519 core0
  ```

- `puppet code deploy` fails with `remote rejected authentication`: the r10k
  key doesn't match gitnano's authorized_keys.  Regenerate it:

  ```bash
  sudo -u gitnano ssh-keygen -y -f /etc/puppetlabs/puppetserver/ssh/id-control_repo.rsa > /opt/gitnano/.ssh/authorized_keys
  ```

- SSH login refused with `System is booting up`: remove the nologin file:

  ```bash
  rm -f /run/nologin /etc/nologin
  ```

## 7.6 Reponano (local apt/yum package repo)

Reponano hosts a local package repo for offline nodes.

**Step 1.** Open the URL from `helper.md` (example `http://core0:3864`).

**Step 2.** Sync a package:

```bash
curl -X POST http://core0:3864/sync \
  -H 'Content-Type: application/json' \
  -d '{"pkg":"sl","distro":"ubuntu","ver":"<codename>"}'
```

**Step 3.** Point a node at the local repo:

```bash
/root/reponano_client.sh core0
```

(`--restore` to go back online.)

**Step 4.** For a full offline pull:

```bash
/root/reponano_full_sync.sh
/root/reponano_forgenano_sync.sh
```

**Verify:** the package is available from the local repo.

## 7.7 Forgenano (local Puppet Forge / module mirror)

Forgenano mirrors Puppet Forge modules to a local repo for offline nodes.

**Step 1.** Open the URL from `helper.md` (example `http://core0:6157`).

**Step 2.** Add a module:

```bash
curl -X POST http://core0:6157/v3/modules \
  -H 'X-API-KEY: <admin-key>' \
  -H 'Content-Type: application/json' \
  -d '{"module":"puppetlabs-stdlib"}'
```

**Step 3.** List all modules in the local forge:

```bash
curl -s http://core0:6157/admin/list -H 'X-API-KEY: <admin-key>'
```

**Step 4.** Populate the full catalog:

```bash
/root/forgenano_populate.sh
```

**Step 5.** (Optional) Use the local workflow helper:

```bash
/root/forgenano_local.sh
```

**Verify:** modules are available from the local forge.

> **Premium modules:** if you provided a Forge bearer token during the build,
> forgenano pulls premium modules too.  The full/premium Puppetfile
> (`Puppetfile.new`) is activated at the end of the build so all modules are
> installed from the local mirror.
>
> **Dynamic populate:** `forgenano_populate.sh` mirrors the built-in catalog
> PLUS every module in the control-repo Puppetfile (`Puppetfile.new` preferred).
> Add modules to the Puppetfile (or use a different control-repo) and they are
> reflected on the next populate — no code change needed.

## 7.95 Pre-release / experimental PE builds

If you need a **pre-release / internal PE build** (e.g. a `2026.0.0-rc` tarball)
instead of a GA release, three things must match: the **PE tarball's platform**,
the **node OS**, and **peadm**.

### What to set (and where)

In `setup_wizard_defaults.json` (or at the wizard prompts), for a 2026.0.0-rc /
Ubuntu 26.04 build:

| Setting | Value |
|---|---|
| `base_os` | `ubuntu-26.04` (one choice → `pe_platform` + Docker base) |
| `pe_platform` | `ubuntu-26.04-amd64` |
| `pe_version` | `2026.0.0` (peadm's `YYYY.M.P` format) |
| `pe_tarball_path` | `/path/puppet-enterprise-2026.0.0-rc0-…-ubuntu-26.04-amd64.tar(.gz)` |
| `custom_image` | `ubuntu-2604` (VM + Docker-host VM image) |
| `docker_base` | `ubuntu:26.04` (container base) |
| `docker_image` | blank (the wizard builds `pe-lab-base:26.04`) |
| `peadm_module_dir` | blank (or a local peadm dir for a custom build) |

### What the wizard does for you
- **Base OS menu** sets `pe_platform` and `docker_base` from the single OS choice.
- **Tarball**: staged as `puppet-enterprise-<version>-<platform>.tar.gz`,
  auto-gzipped from a `.tar`, and **validated** (a truncated download fails fast).
- **peadm**: since `2026.0.0 > 2025.11` (`peadm_newest`), the wizard sets
  **`permit_unsafe_versions = true`** in the peadm params so it accepts the
  unknown version (`lib/artefacts.sh`). To use a specific peadm, set
  `peadm_module_dir` — the wizard installs it into
  `~/.puppetlabs/bolt/modules/peadm` (`lib/deps.sh`).
- **Docker base**: the multi-OS Dockerfile is built `FROM docker_base` and tagged
  `pe-lab-base:<os-version>` (Ubuntu 24.04/26.04, RHEL 8/9).
- **PDK**: `ensure_pdk.sh` installs PDK (needed by forgenano) with a codename
  fallback, so brand-new OS codenames work.

### Verify after provisioning
```
ssh -i <key> -p 2201 root@<docker-host>
docker exec <core0> cat /etc/os-release   # node OS must equal the PE platform
```
If you see *"attempting to use a ubuntu-26.04 tarball on ubuntu-24.04"*, the
container OS doesn't match the tarball — check `base_os`/`docker_base` and rebuild
with a matching base image.

## 8. Day-2 operations

### Restarting the Docker host

The containers were started with `--restart unless-stopped`, so when the VM
reboots, Docker automatically restarts every container and the PE services come
back up.  After the host is back, the console and agents are reachable again
without re-running the wizard.

### Stable `/etc/hosts` connections

- Every connection (console, agents, SSH) relies on `/etc/hosts` entries that
  map the Docker host's **internal network IP** to the container FQDNs.
- The internal IP is **stable** across VM restarts and present even in
  air-gapped environments.
- The wizard host must be on the same internal network to reach it.
- The wizard host's `/etc/hosts` is updated automatically on each run.  Your
  laptop and agent nodes are **not** — update them manually.
